# 原始需求诊断与优化提示词

日期：2026-10-16。任务类型：源码审查、发行物逆向、技术研究与文档；范围较大，分阶段执行，不涉及本轮实现或发布。上下文已检测为 Java 21、Maven、XhlCLI 1.0.1。

## 1. 提示词诊断

原需求的优点：明确指定了自己的项目、两个对照产品、需要调用的技能，以及“讲明白原理、找到改进方向”的最终目的。

| 缺口 | 影响 | 优化方式 |
|---|---|---|
| “源码”未区分开发仓库和发行制品 | 容易把压缩包、类型声明或官网宣传冒充完整源码 | 固定样本版本、格式、哈希和证据类型 |
| Review 未定义问题标准 | 容易退化成代码风格建议或功能清单 | 要求位置、触发、影响、复现、修复方向 |
| “傻子都能看懂”未定义阅读结构 | 容易只堆术语或过度简化 | 使用一个工程任务贯穿、流程图、术语表和对应代码 |
| 优化与拓展未排序 | 建议太多，无法决定下一步 | 分正确性、平台能力、产品实验，比较成本和收益 |
| 没有明确本轮副作用 | 容易顺手修代码、更新环境或发布 | 限定只读业务源码，允许报告和临时离线验证 |
| 缺少验收与未知边界 | 容易把静态推断说成运行事实 | 每项结论注明观察/文档/推断/未知，保留失败覆盖 |

需要澄清的事实已由现有上下文和保守边界处理：目标目录已指定，技术栈自动检测，报告采用简体中文，默认不修改业务行为、不启动真实模型任务、不接入账号、不发布。新功能只作为候选，不替用户决定 Phase 19 范围；本轮不需要因这些默认值再次阻塞用户。

## 2. 推荐编排与实际能力

| 类型 | 能力 | 职责 |
|---|---|---|
| 顶层编排 | 用户指定的 `vibe-workflow` | 确认基线、范围、文档事实源与完成证据 |
| 提示词阶段 | 用户指定的 `prompt-optimizer` | 只诊断和优化提示词；完成后返回顶层编排 |
| 源码审查 | 普通仓库读取、定向调用链追踪、离线探针 | 完整源仓库不需要跑 REA |
| 外部获取 | 用户指定的 `agent-reach` | Exa、Jina、GitHub 路由；临时获取文件放 `/tmp` |
| 发行物分析 | 用户指定的 `reverse-engineer-anything` | 真实制品、REA Evidence、精确静态切片和未知范围 |
| 并行工作 | 源码、Claude 发行物、Qoder 发行物独立分工 | 按 REA 广泛调查的并行要求执行，由一个 owner 汇总 |
| 模型 | 沿用当前会话模型 | 不凭技能旧版本表格推荐未核实的模型名称 |
| 验证 | Maven 现有测试、假模型、临时目录探针、文档检查 | 验证关键结论，不以模型自评代替结果 |

不将技能文档里的示意 `/plan`、`/code-review`、`/verify` 当成当前环境已存在的命令。实际工作流为：事实基线→问题与证据清单→并行调查→定向复现→对照与排序→文档验收。

## 3. 优化提示词：完整版

```text
请以 xhlcli/ 当前工作区为对象，完成一轮源码审查、Claude Code 与 Qoder 发行物技术分析，并形成面向初学者的简体中文报告。

已知项目是 Java 21 + Maven 的本地终端 Coding Agent。先读取适用 AGENTS.md、Document Map、当前进度和构建入口，用 Git 和源码核对实际版本；保留用户已有改动，计划能力不能当成已实现能力。

使用 vibe-workflow 作为唯一顶层编排。先使用 prompt-optimizer 产出本次任务的提示词诊断与优化稿，结束提示词阶段后继续执行，不停在建议层。

阶段一：审查本项目。
重点追踪 Agent 循环、模型适配、统一工具管线、权限与路径、取消与超时、上下文压缩、检索、并发、多 Agent、快照、后台任务和 Runtime 入口。
优先报告实际行为缺陷。每项发现提供优先级、准确文件与行号、触发条件、影响、最小复现或验证依据、修复方向和建议回归场景。把缺陷、能力缺口和产品建议分开。

阶段二：分析竞品。
用 agent-reach 获取官方安装说明、文档、GitHub 和发行元数据；下载和临时采集写入 /tmp。
用 reverse-engineer-anything 分析能合法取得的已分发制品。先确定目标身份、版本、格式和哈希，保留 REA Evidence ID、命令、覆盖限制和精确函数锚点。
当前版本无法分析时，可以另取官方历史 JavaScript 版本，但必须醒目标注历史版本，不能冒充当前实现。大包分析失败时保留失败证据；局部切片要记录原文件哈希、字节范围和片段哈希。
重点回答：Agent 回路如何组织；工具如何校验、授权与取消；如何管理上下文、大输出和记忆；子代理如何隔离；Skills、Hooks、MCP 和 SDK 如何连接；长任务如何恢复与验证。
若只能取得 CLI、类型契约或官方文档，明确它们不等于 IDE、服务端或完整开发源码。

阶段三：用初学者能理解的方式讲解。
用“修改一个接口并运行测试”的实例贯穿解释模型、Agent 程序、工具、权限、上下文、记忆、检索和事件；提供一张流程图和术语表，再映射到本项目类和竞品证据。
每个重要结论区分源码观察、制品静态观察、官方说明、推断和未知。静态代码存在不能当作运行可达、默认启用或安全保证。

阶段四：给出可执行的候选路线。
逐项对照本项目已有实现，避免重复建议已完成能力。
按“先修正确性→补运行时和上下文→拓展产品功能”排序，列收益、相对成本、依赖、风险边界和验收办法。
重点考虑本项目的 Java 优势和可复用基础，不为追赶功能数量同时开放所有方向。

交付：
1. 一份中文主报告：审查发现、通俗讲解、功能对照和优先路线。
2. 完整与简版优化提示词。
3. Claude Code / Qoder 的版本、哈希、Evidence 和范围附录。
4. 本项目测试与复现的命令、结果和证据索引。
5. 在已有研究与进度入口加入本次报告导航，保留历史发布事实。

验收：运行适用的现有测试；关键缺陷尽量用假模型和临时目录复现；所有本地报告链接可定位；结论能追到代码或来源；原始调查问题标明已回答、部分回答或未知；写明尚未验证的真实环境。

本轮允许生成报告、临时离线探针和必要证据；不修改业务实现，不提交或推送，不升级或配置系统分析引擎，不登录竞品或访问用户凭据，不调用真实付费模型，不把建议写成已经批准的新 Release。
```

## 4. 优化提示词：简版

```text
用 vibe-workflow 编排：先优化本提示词，再 Review xhlcli 当前 Java21/Maven 源码；用 agent-reach 获取官方资料，用 REA 分析固定版本的 Claude Code、Qoder 发行物。关键缺陷给准确代码位置、触发条件、离线复现和修复验收。用通俗中文和流程图讲清工作原理，再按收益、成本、依赖排列优化与拓展路线。保留版本、哈希、Evidence、静态覆盖和未知；不把文档或历史样本冒充当前实现。输出主报告与证据附录，运行现有适用测试并核对链接。本轮只生成报告与离线验证，不改业务、不发布、不登录或调用真实模型。
```

## 5. 增强理由

| 增强 | 理由 |
|---|---|
| 版本和证据分级 | 防止竞品变化、混淆文件和不完整分析误导结论 |
| 问题必须可触发和复核 | 让 Review 可以直接转为修复任务 |
| 明确技能职责交接 | prompt-optimizer 本身是咨询技能，执行由用户授权的顶层流程继续 |
| 先看现有实现再提建议 | 减少重复建设，识别真正阻塞体验的缺口 |
| 给路线加验收 | 让“值得做”能转化为下一轮可测需求 |
| 记录未知与未验环境 | 让后续调查直接补缺，而不是重复或夸大结论 |

本优化稿已按用户“优化后开始任务”的授权进入执行；主报告记录实际产出与验证情况。
